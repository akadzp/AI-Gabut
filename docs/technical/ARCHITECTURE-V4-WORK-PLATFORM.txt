AI-GABUT ARCHITECTURE V4 — AGENTIC WORK PLATFORM

PURPOSE
=======

V4 adalah product/workflow layer yang menggunakan V2 AI Foundation dan
V3 Agentic Application + Integration Foundation.

Tujuan pembuktian utama V4 adalah AI + GitHub development workflow.

V4 tidak membangun Agent Engine kedua dan tidak membuat connector
provider-specific menjadi bagian dari generic core.

LAYER
=====

    User
      ↓
    V4 Agentic Work Surface
      ↓
    Work / Task / Execution Orchestration
      ↓
    V3 Agentic Application Foundation
      ↓
    V2 AI / Agent Foundation
      ↓
    Connectors / External Providers

NORTH STAR
==========

AI-Gabut harus dapat menjadi execution platform untuk pekerjaan
development.

AI capability dan external capability adalah platform capability yang
dapat dikombinasikan.

AI + GitHub adalah first proving workflow:

    V2 AI Foundation
          +
    V3 GitHub / Integration Foundation
          ↓
    V4 Development Work Platform

PRIMARY OBJECT
==============

Work menjadi abstraction utama di atas session dan execution.

    Project
      ↓
    Work
      ├── objective
      ├── context
      ├── plan
      ├── tasks
      ├── executions
      ├── changes
      ├── approvals
      ├── evidence
      └── result

FRONTEND ROLE
=============

Frontend V4 adalah control surface, bukan authority layer.

Ia menampilkan:
- objective
- plan
- progress
- action status
- approval state
- changes / diff
- verification
- repair/replan
- evidence
- artifacts
- result
- recovery state

Ia tidak menampilkan atau menyimpan hidden chain-of-thought sebagai
product requirement.

AUTHORITY
=========

V4 meminta capability.
V2/V3 security authority menentukan permission dan approval.
V4 tidak dapat melewati policy melalui UI atau orchestration.

AUTONOMY BOUNDARY
=================

Autonomous loop harus memiliki:
- capability boundary
- authorization
- approval bila diperlukan
- checkpoint
- timeout
- retry / loop limit
- cancellation
- recovery
- escalation to human

VERIFICATION
============

V4 tidak menganggap perubahan sebagai sukses hanya karena Agent
menghasilkan response.

Outcome harus dapat didukung oleh evidence:
- tests
- tool result
- diff
- external check
- CI result
- artifact
- provider state

AI + GITHUB DEVELOPMENT WORKFLOW
=================================

Contoh target:

objective
 → understand
 → plan
 → authorize
 → act
 → verify
 → repair/replan
 → review
 → commit/push/PR
 → CI
 → repair if needed
 → final result

Provider-specific implementation tetap berada di connector.
Workflow orchestration tetap berada di V4/application layer.

GITHUB BOUNDARY
===============

GitHub:
- tetap berada pada connector/integration boundary;
- menyediakan external repository/change/PR/CI capability sesuai scope;
- tidak menjadi dependency langsung generic Agent Engine.

V4:
- mengorkestrasi work;
- memilih capability;
- menyimpan work state;
- mengelola verification dan repair;
- menghubungkan external feedback ke work lifecycle.

MULTI-USER
==========

Work, task, execution, approval, changes, evidence, artifacts, dan
result yang user-owned harus mengikuti ownership enforcement yang
sudah berlaku di V3.

RECOVERY
========

Long-running work harus dapat mempertahankan durable state dan
melanjutkan execution valid setelah reconnect/restart sesuai capability
reliability layer.

V4 tidak boleh menyamakan reconnect frontend dengan restart execution.
Durable execution state tetap menjadi source untuk continuity.

BOUNDARY RULE
=============

Jika sebuah capability:
- generik terhadap application,
- tidak membutuhkan identity Agentic,
- dan berguna bagi lebih dari satu consumer,

maka pertimbangkan untuk menempatkannya pada platform/core/connector
boundary.

Jika sebuah capability:
- merupakan workflow produk,
- bergantung pada work UX,
- mengorkestrasi beberapa capability,
- atau merupakan proving use-case AI + GitHub,

maka default-nya berada di V4/application/work layer.
