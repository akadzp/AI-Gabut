Batch 158 — Key-Lifecycle External Checkpointing, Manifest-Ledger Freshness/Retention Audit, and Revalidation Lease Contention/Crash-Recovery Hardening

- Added an independent external snapshot checkpoint for the attestation signing-key lifecycle. The checkpoint binds the initial key ID, public-key fingerprints, and digest-linked rotation/revocation events. Enrollment is explicit; reconciliation advances only one provable lifecycle event at a time. A changed public-key registry with unchanged event count is treated as source drift and cannot be silently reconciled.
- Added application APIs and authenticated HTTP routes for key-lifecycle checkpoint status, explicit enrollment, one-event continuity reconciliation, and audit. The trust domain participates in checkpoint policy-binding audit coverage and endpoint/provider independence enforcement.
- Added a read-only manifest-approval ledger freshness/retention audit. It reports checkpoint freshness, timestamp integrity, ledger-event age, and retention-review due state. Stale checkpoints take precedence over retention-review status; no event is deleted or compacted.
- Hardened durable revalidation leases with schema-versioned record links, monotonic fencing-token transition validation, legal action-transition checks, expiry/renewal consistency, and explicit `recovery_required` status for expired active leases. Legacy lease records without the new record-link fields remain auditable as `history_unproven` rather than being silently treated as fully proven.
- Added tests for key lifecycle rotation/revocation across application restart, registry drift rejection, manifest-ledger retention and stale-checkpoint behavior, real OS-process lease contention over a shared atomic store, and recovery after a crashed lease owner. The stale worker remains fenced after recovery.
